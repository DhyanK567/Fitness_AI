# Day 4-5 SL + ERPE verification record

## Scope and implementation evidence

- ERP paid-event registration, payment holds, and idempotent hold expiry are implemented in the custom Frappe app.
- Membership expiry now re-locks and rechecks each candidate's Active status and end date before updating it and queuing the signed callback; the repeat-run contract test confirms only the successful transition emits the callback.
- Booking retries recheck their idempotency key after obtaining the session lock, a tenant-scoped unique key protects races across different sessions, active membership eligibility is locked against expiry transitions, and cancellation now uses the same session-before-booking lock order as booking/promotion.
- Payment webhook processing claims are conditional, recover stale processing claims, permit retry after failure, and persist the audit/outbox and processed status in one tenant-scoped transaction.
- Frappe migration hooks now install tenant-scoped unique constraints for member email/phone, plan names, class names, staff email, schedule/date, booking idempotency keys, payment provider references/idempotency keys, and attendance; tenant-leading lookup indexes cover membership expiry, session lists, booking queues/history, leads, payments, and event registrations. The manifest is checked against actual DocType fields. Existing duplicate rows will make index creation fail visibly rather than silently weaken the constraint.
- The ERPE contract suite enforces exactly 20 ERP DocTypes, matching the Database Design Document, and requires every defined DocType (including child tables) to be covered by the generic-access denial hook.
- ERP-originated callbacks use an HTTPS target, HMAC-SHA256 signatures, and enqueue-after-commit delivery.
- Gateway webhook handlers preserve the raw request body for Razorpay and ERP signature verification.
- Gateway boundaries include an origin allow-list, request-size limit, global DTO validation, and staff login rate limiting.
- Proxy-derived client IPs are disabled by default; production requires an explicit bounded `TRUST_PROXY_HOPS` value so IP-based throttling does not silently trust forwarded headers from an unknown topology.
- Host tenant codes resolve to active platform tenants; platform UUIDs and Frappe tenant codes remain distinct.
- The SL Settings API is included in OpenAPI and exposes only the public key/value shape; setting writes are bounded, tenant-scoped, cache-invalidating, and audited.
- Staff lifecycle rules protect the last active tenant owner with a per-tenant transaction lock, revoke sessions on deactivation, and audit status changes.
- Staff passwords now use Argon2id via `@node-rs/argon2` as required by the Database Design Document and compatible with the documented Node 20+ baseline. Legacy scrypt hashes are still verified and upgraded on successful login with a credential compare-and-set; if a concurrent reset/change replaced the verified hash, login fails without issuing a session. Invite, reset and password-change flows all store Argon2id hashes. An interoperability test verifies existing PHC Argon2id hashes generated by the previous implementation.
- Password change now updates credentials with a compare-and-set against the exact hash that was verified, so an in-flight change cannot overwrite a concurrent reset; sessions are revoked only after that compare-and-set succeeds.
- Gateway startup now rejects a missing or unrecognized `NODE_ENV`; member OTP returns a test code only when `OTP_MODE=mock` and the explicitly configured environment is development or test. Missing runtime mode fails closed.
- ERP callback jobs no longer serialize the HMAC secret in the queue payload; the worker reloads it from protected Frappe site configuration at delivery time.
- ERP callback contract specifies the exact raw-body HMAC header and the narrowly allowed tenant header; the receiver validates UUID/event/resource/payload shape before idempotent processing.
- ERP adapter exposes only the assigned health/version diagnostics; the unrelated endpoint that revealed the shared integration account identity has been removed.
- ERP adapter maps allowlisted Frappe validation, missing-record, duplicate-conflict, and permission exceptions to the contract's 400/404/409/403 statuses. Missing methods, integration-auth faults, and unknown upstream errors remain generic gateway failures; Frappe stack traces are never returned to clients.
- ERP adapter does not infer a caller conflict from a generic Frappe `NameError` label unless the HTTP status is the documented conflict status or the exception is specifically `DuplicateEntryError`.
- ERP adapter only maps conflicts from HTTP 409; misleading duplicate/name exception labels attached to HTTP 500 remain generic service-unavailable failures.
- Staff/public request throttling uses tenant-scoped PostgreSQL buckets with HMAC client keys and atomic upserts, so the counter is shared across API replicas. Runtime RLS and concurrent update behavior still require real PostgreSQL verification.
- Tenant-owned Prisma queries set transaction-local `app.tenant_id`; migrations define forced PostgreSQL RLS policies. Unit tests cover the context wiring, but only a real database test proves policy behavior.
- Audit and security-event tables revoke `UPDATE`/`DELETE`/`TRUNCATE` from `PUBLIC` and, when the documented `app_rw` role exists, revoke the same privileges from it; row triggers reject updates/deletes and statement triggers reject `TRUNCATE`. Effective privileges, role memberships, ownership, and RLS still need verification against real PostgreSQL; SQL contract tests do not substitute for applying the migration.
- Audit snapshots now pass through resource-specific field allowlists: staff snapshots retain only status/role codes, settings snapshots retain only the setting key, and unsupported resource snapshots are omitted. This prevents the invite/member PII and raw arbitrary settings JSON previously passed by callers from being stored in audit `before_data`/`after_data`.
- The HTTP middleware now binds bounded IP, route, user-agent, and correlation context using async-local request scope; the shared audit writer adds it to each audit row without relying on every module to forward metadata manually.
- Security events support nullable, non-FK tenant references so pre-resolution signals survive tenant removal; RLS permits tenantless inserts but tenant-scoped reads remain limited to the current tenant. They include indexed IP/route fields, populated by SL-owned staff, Razorpay and ERP-callback signature-failure writers. Verify this policy/index/FK behavior with real PostgreSQL roles and tenant contexts before release.
- The SL-owned `StaffAccessGuard` applies only tenant-wide role assignments and permission grants while request authorization resolves tenant only. Studio/branch assignments and resource-scoped grants fail closed rather than being widened there. The member-or-staff guard in the separate booking-domain tree was not changed because it is outside this ownership scope; its scoped assignment/grant behavior needs that domain owner’s review before such grants are issued.
- Staff RBAC resolution and permission evaluation now live in `src/platform/roles-permissions/PolicyService`, which is wired through the global policy module and checks the current session, active staff identity, tenant-wide roles, grants, and required permission on each request.
- Frappe blocks generic DocType access for non-Administrator users; whitelisted APIs still require the dedicated restricted identity and active matching tenant, and tenant list filters fail closed for other users.
- Frappe permission contract tests verify tenant query filters fail closed without request context, reject an identity with extra business roles, escape tenant codes as SQL literals, allow generic DocType access only to Administrator, and register a query-condition hook for every parent DocType.
- OTP failure counts use conditional atomic updates, and successful verification consumes the challenge with a compare-and-set before issuing account/session side effects.
- OTP request limits use a PostgreSQL transaction advisory lock per tenant/phone so count-and-create is serialized across gateway instances; refresh rotation and password-reset consumption also use conditional one-time updates.
- Google member sign-in validates ID tokens with the configured OAuth audience; only previously linked identities can sign in. Account linking checks the persisted authentication time on the live, unrevoked database session (preserved through refresh-token rotation), not the refreshable access-token `iat`, and audits the link. Email matching alone never links accounts.
- Member OTP and Google sign-in re-check the linked Frappe member record and fail closed unless its ERP identity matches and its status is active. Registration does not create a platform user or issue a session while Frappe reports pending/inactive status.
- In production, the gateway requires `FRAPPE_EXPECTED_APP_VERSION` and fails startup if the restricted ERP adapter cannot verify the installed `wellness_studio` version.
- ERP callbacks verify that the signed tenant matches the tenant resolved from the request host.
- Razorpay order retries reconcile by deterministic receipt and validate tenant, member, target, amount, and currency before returning a recovered order.
- Membership activation refuses unpaid records; membership payment posting checks the immutable plan-price snapshot and marks payment/membership state together in the ERP transaction.
- Paid event confirmation locks the event/registration/payment records and requires a Paid event-purpose record matching tenant, registration, member, and event price before confirming a hold.
- Attendance check-in accepts only the three documented methods; correction status and reason inputs fail closed on non-string/invalid values, and corrections retain the locked before/after audit trail.
- Member create/update endpoints reject malformed field types, validate and normalize bounded phone/contact fields, and refuse to reuse a tenant phone for a different name/email; matching retries use tenant+phone uniqueness, with concurrent duplicate recovery. The unused member `idempotency_key` argument was removed rather than implying a guarantee it did not provide.

## Scope alignment and ownership-boundary gaps found during PDF audit

- The Database Design Document specifies 20 ERP DocTypes. The undocumented `WS Member Class Preference` child DocType and its Member field were removed so the source schema matches that exact inventory; the booking assistant's conversational preferences remain transient as described by its documented flow. The generic-access denial hook covers the remaining DocTypes, including child tables.
- The gateway declares `leads:read` and `leads:write` on lead routes. Both codes are now included in the tenant IAM seed and assigned to Admin; a contract test checks that every gateway permission code exists in the seed. The Module Specification assigns Front Desk lead capture/status updates but not conversion, while the current lead controller reuses `leads:write` for create, update, convert, and deactivate. I did not grant that broad permission to Front Desk or edit the separately owned lead-domain routes. Front Desk CRM authorization remains incomplete until the domain owner splits the sensitive permission and the role matrix is reconciled.
- The Module Specification's role matrix is finer-grained than several current domain permissions: Front Desk's seeded `members:write` also authorizes member deactivation, `memberships:write` also authorizes membership create/cancel, `events:write` authorizes event create/edit/cancel, and `attendance:write` authorizes corrections that the specification reserves for Owner/Admin. Trainer `members:read` currently reaches tenant-wide member list/detail endpoints although the specification limits Trainers to assigned-session participants and a reduced profile. These are not safe to solve by broadening or special-casing the central guard: action-level route permissions and trainer record scoping are required in the separately owned domain controllers/services. This audit did not modify those files; do not release the affected role capabilities as compliant with the role matrix until their owner resolves them.
